# 适配、已有优化与新上游方案的关系

这个项目的工作可以分成三层。它们是工程上的叠加关系，不是每个 token 依次经过的三个计算步骤。

## 第一层：运行适配

我们沿用作者提供的量化权重。需要适配的是它在本机上的执行路径：在研究时固定的上游版本里，部分预填充矩阵计算使用 NAX 相关实现，而 M2 不能直接使用同一路径。我们参考可在 M2 使用的 SIMD 实现，保留对应 EXL3 码本、数据读取和数值规则，替换必要的计算部分。

1017 包的主干专家混合 K2／K3，九月版的 K3-only 适配库不覆盖全部入口。因此还需要在上游已经提供的混合位宽支持之上，迁移 M2 算子适配，核对记录尺寸、每层布局、临时缓冲、源码／头文件标识及回收边界。这不等同于重新量化，也不把上游已有的 K2 支持算作我们的原创。

宿主和插件也需要配套：请求模板、文本／工具协议、原生状态传递、阶段切换、错误处理和内存准入不能任意混用版本。当前仓库固定了它们的版本和修改。

代码位置：

- [`m2/kernel_patch.c`](../m2/kernel_patch.c)：精确源代码匹配的 M2 适配库，同时包含已经积累的算子优化；不是任意版本通用的替换库。
- [`mlx-serve.patch`](../patches/mlx-serve.patch)：宿主接口、请求与模板等集成修改。
- [`mlx-stream-baseline.patch`](../patches/mlx-stream-baseline.patch)：插件适配与此后已有优化的合并补丁。
- [`sources.lock.json`](../sources.lock.json)：上游版本、文件前后指纹和模型修订。

上述“需要适配”的结论针对本项目固定版本和本机验证，不是对所有后续上游版本、其他引擎或所有 Apple Silicon 机器的断言。

## 第二层：已有的本地优化

这部分是在能运行之后逐步积累的，不依赖最后一次选择性缓存适配才存在。

| 工作 | 当前实现中的对应内容 | 说明 |
| --- | --- | --- |
| 输入阶段命中优先及跨批次处理 | `HITS_FIRST`、`HITS_FIRST_ROLLING`、`prefill_suffix` | 减少可以避免的输入等待与重复处理 |
| 专家计算复用 | M2 适配库的 `GU_PAIR` 路径 | 参考已有实现进行本地适配和数值验证；不能把算子微测直接当整模型收益 |
| 已生成回答状态复用 | `ANSWER_CHECKPOINT`、`committed_tokens` | 保留能够继续对话的完整状态，而不只保留原输入的部分前缀 |
| RAM／SSD 会话状态 | `session_pool`、`session_disk`、`session_codec` | 用原生状态和身份校验支持复用；不是仅把聊天文字写入磁盘 |
| 长历史短后缀 | `LONG_PREFIX_PARK` 及请求身份／预算检查 | 新增输入和已有历史位置分开核算，避免把长历史当短上下文 |
| 专家记录复用 | `PARK_RECORDS`、`PARK_COPY`、固定专家统计 | 复用已有记录，是第三层继续改进的基础 |
| 服务兼容与可靠性 | 宿主补丁、`web/` 及服务脚本 | 包含接口、流式超时、监控和回滚；不笼统算成 TPS 优化 |

这些名称用于定位代码，不表示每项都有独立、可相加的收益百分比。当前启用情况见 [`config/profile.json`](../config/profile.json)。方法来源与本地修改应同时保留，见 [NOTICE](../NOTICE)。

## 第三层：对新上游 PR／提交的选择性适配

本次参考固定到 Sushi [`b68302a`](https://github.com/beamivalice/sushi/blob/b68302a1469ed7d2dab03530cc10c6e2685f2a0a/src/dsv41_borrow.zig)。我们采用按工作内存需求释放必要缓存的做法，并把它接入当前 EXL3 引擎。

本地实现的关键差异：

1. 按本地 K2／K3 每层的实际扩展缓存所有者计算字节数，而不是照搬 STQ 的权重与容量公式。
2. 保留基础缓存，仅释放必要的后部扩展缓存；GPU／I/O 完成同步并解绑后才释放，缺失专家仍使用原读盘路径。
3. 释放计划不能直接作为空闲内存。等待并重新读取真实占用，通过原生预算后才分配输入工作区。
4. 处理 macOS 全局统计可能返回旧值的问题，避免刚释放后因旧读数继续丢弃有用缓存。
5. 现阶段只启用已验证的短新增输入／长历史短后缀范围。其他上游新方法没有因“作者有效”就自动启用。

对应 [`mlx-stream-selective-cache.patch`](../patches/mlx-stream-selective-cache.patch)，主要涉及 `partial_park`、`parked_ext`、`module`、`bill` 与专家缓存所有者操作。它是在前两层之上的增量补丁。

## A／B 到底比较什么

| 构建档位 | 包含的工作 |
| --- | --- |
| `baseline` / A | 第一层运行适配＋第二层已有优化 |
| `optimized` / B | 与 A 相同的内容＋第三层选择性缓存适配 |

因此，README 中的约 5.9% 总耗时改善是第三层的增量证据。它既不是原作者方案在 M2 上从“不能跑”到“能跑”的百分比，也不是所有历史优化的总和。

两版都使用同一量化模型、M2 适配库、224／288 缓存和 256K 配置。具体提示词、采样、计时和已知限制见 [测速说明](BENCHMARKS.md)。
